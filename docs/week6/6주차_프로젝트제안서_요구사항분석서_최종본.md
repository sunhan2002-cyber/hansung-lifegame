## 1. 프로젝트 제안서

### 1.1 제안 배경

사용자는 짧은 시간 안에 선택의 결과를 확인할 수 있는 모바일 게임을 선호하지만, 단순 선택형 텍스트 게임은 선택의 결과가 즉시 끝나거나 반복 플레이의 이유가 약한 경우가 많다. 우리 팀은 선택이 누적되어 능력치, 사건, 결말에 영향을 주는 인생 시뮬레이션을 Android 앱으로 구현하여, 사용자가 한 번의 선택이 이후 흐름에 어떤 영향을 주는지 확인할 수 있는 게임을 만들고자 한다.

### 1.2 주요 사용자층과 사용 목적

주요 사용자는 짧은 플레이 시간 안에 스토리와 결과를 즐기고 싶은 모바일 게임 사용자, 선택형 시뮬레이션을 좋아하는 사용자, 여러 결말을 수집하고 싶은 사용자다. 사용 목적은 한 회차를 끝까지 플레이하며 자신의 선택 경로와 최종 결과를 확인하고, 다른 선택으로 재시작해 다른 삶의 흐름을 비교하는 것이다.

### 1.3 기존 선택형 게임과의 차별점

기존 선택형 텍스트 게임은 선택지가 다음 문장으로만 이어지는 경우가 많다. 본 프로젝트는 건강, 운동능력, 지력, 사회성, 경제력, 행복, 운 지표를 누적하고, 조건부 사건과 돌발 사건, 결말 판정에 연결한다. 7주차 이후 v4 단계에서는 시기별 초점, 자동 진행, 결정 사건, 주마등 기록, 도트풍 장면을 추가하여 사용자가 자신의 성장 흐름을 더 직관적으로 볼 수 있게 한다.

### 1.4 기술 스택과 활용 목적

| 기술 | 활용 목적 |
|---|---|
| Kotlin | Android 앱의 화면 상태, 게임 로직, 데이터 모델 구현 |
| Jetpack Compose | 시작 화면, 캐릭터 설정, 게임 진행, 결말 화면 구현 |
| ViewModel | 화면 상태와 게임 세션 상태 관리 |
| JSON assets | 사건, 선택지, 결말, 이미지 ID 등 콘텐츠 데이터 관리 |
| Gradle | 단위 테스트와 debug APK 빌드 검증 |

### 1.5 v4 개발 단계의 의미

v4는 현재 구현된 기본 선택형 게임을 다음 개발 단계로 확장하기 위한 설계 버전이다. 현재 앱은 새 게임 시작, 캐릭터 설정, 사건 선택, 능력치 갱신, 결말 판정까지의 기본 흐름이 구현되어 있다. v4에서는 시기별 초점, 자동 진행, 결과 확률, 숨은 결과 처리, 도트풍 장면, 주마등 기록을 추가하는 것을 목표로 한다.

### 1.6 프로젝트 성공 기준

| 기준 | 성공 조건 |
|---|---|
| 게임 완료 | 새 게임 시작부터 결말 화면까지 강제 종료 없이 진행된다. |
| 핵심 기능 | 캐릭터 설정, 사건 표시, 선택 반영, 다음 사건 이동, 결말 판정이 동작한다. |
| 저장·복원 | 저장 데이터가 있을 때 이어하기가 같은 진행 상태를 복원한다. |
| 데이터 확장 | 사건과 결말을 JSON으로 추가할 수 있고 화면 코드 수정 없이 로드된다. |
| 검증 | 콘텐츠 검증, debug 빌드, 주요 로직 테스트 결과가 기록된다. |

## 2. 개발 단계와 요구사항 작성 기준

요구사항 ID는 요구사항을 추적하기 위한 문서용 식별번호다. 강의자료의 요구사항 분류 방식에 따라 기능, 데이터, 화면, 테스트, 비기능, 개발 관리 요구사항을 구분한다. 구현 완료 여부는 ID와 별개로 상태 열에서 표시한다.

### 2.1 구현 상태 판단 기준

| 상태 | 판단 기준 |
|---|---|
| 구현됨 | 현재 Kotlin 코드, JSON 데이터, 테스트 파일에서 확인 가능한 항목 |
| 일부 구현 | 기본 구조는 있으나 예외 처리, 화면 연결, v4 확장이 남은 항목 |
| 설계 확정 | 팀 문서와 v4 개편안에 포함되었으나 현재 앱에는 아직 완전 반영 전인 항목 |
| 계획 | 후순위 확장 기능으로 문서화되었지만 개발 범위가 확정되지 않은 항목 |

### 2.2 우선순위 기준

| 우선순위 | 의미 |
|---|---|
| 필수 | 앱 기본 실행과 과제 제출에 반드시 필요한 항목 |
| 중요 | v4 개편 품질과 사용자 경험에 직접 영향을 주는 항목 |
| 선택 | 시간이 남을 때 확장하거나 후순위로 구현할 수 있는 항목 |

| DR-05 | 저장 상태 데이터 | 필수 | 일부 구현 | DB·QA | 저장 상태는 runId, stage, currentEventOccurrenceId, screenState, stats, flags, history를 포함한다. | 저장 후 로드 시 동일한 상태가 복원된다. |

### 5.2 DR-01 사건 데이터 필드 정의

| 필드 | 자료형 | 필수 | 허용값/기본값 | 설명 |
|---|---|---|---|---|
| eventId | String | 필수 | 중복 불가 | 사건 고유 ID |
| stage | String | 필수 | INFANT, CHILD, TEEN, ADULT | 현재 구현 기준 성장 단계 |

| title | String | 필수 | 빈 문자열 불가 | 사건 제목 |
| text | String | 필수 | 빈 문자열 불가 | 사건 본문 |
| imageId | String | 필수 | image_ids에 존재 | 화면에 표시할 이미지 참조 ID |

### 5.3 데이터 간 관계

사건 데이터는 선택지 데이터를 포함하고, 선택지는 능력치 변화와 플래그 변화를 만든다. 진행 상태는 현재 사건, 완료 사건, 선택 기록, 능력치, 플래그를 저장한다. 결말 데이터는 최종 능력치와 플래그 조건을 참조한다. 이미지 데이터는 사건과 기록 화면에서 imageId로 연결된다.

## 10. 데이터 흐름도

### 10.1 그림 1. Context Diagram

Context Diagram은 외부 주체와 시스템 사이의 입출력만 표시한다. 내부 데이터 저장소는 표시하지 않고 Level 1 DFD에서 정의한다.

- 사용자 → 시스템: 새 게임 요청, 캐릭터 정보, 선택값, 이어하기 요청
- 시스템 → 사용자: 사건 화면, 선택 결과, 능력치 변화, 저장 오류 안내, 결말
- 콘텐츠 관리자 → 시스템: 검증된 사건 데이터, 이미지 ID 데이터, 결말 데이터
- 시스템 → 콘텐츠 관리자: 데이터 검증 결과, 누락 참조 목록, 빌드/테스트 결과

### 10.2 그림 2. Level 1 DFD

Level 1 DFD는 게임 실행 순서가 아니라 데이터가 처리되는 흐름을 기준으로 작성한다. 사용자 선택값은 선택 결과 계산 프로세스로 전달되고, 계산 결과는 진행 상태 저장소에 반영된 뒤 다음 사건 판정으로 반복된다. 저장 데이터와 복원 데이터는 별도 흐름으로 구분한다.

## 11. 화면 이동 흐름

```text
시작 화면
  → 캐릭터 설정 화면
  → 게임 진행 화면
  → 선택 결과 표시
  → 다음 사건 또는 결말 화면
  → 다시 시작 시 시작 화면
```

저장 데이터가 있는 경우 시작 화면에서 이어하기를 선택해 게임 진행 화면으로 복원한다. 저장 데이터가 없거나 손상된 경우 새 게임 안내를 표시한다.
